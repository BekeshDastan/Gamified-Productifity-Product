## 1. Назначение и границы проекта

### 1.1. Что строим

ASCEND — адаптивное веб-приложение, в котором реальные действия представлены как квесты. Пользователь планирует день, выполняет задачи и привычки, продвигается к целям, получает опыт и косметические награды, участвует в испытаниях и анализирует собственную регулярность.

Основной цикл продукта:

```text
Цель → этапы → задачи и привычки → план в календаре
     → выполнение / честная фиксация пропуска
     → прогресс + опыт + достижения
     → вечерний разбор → корректировка следующего плана
```

Продукт должен быть полезен даже при полностью отключённых игровых анимациях, социальных функциях и внешних интеграциях.

### 1.2. Обязательные принципы

- Реальный результат важнее XP. Создание задач, открытие сайта и количество кликов сами по себе не приносят опыт.
- Отдых допустим. Пропуск не отнимает заработанные уровни, не создаёт штрафы и не вызывает унижающих уведомлений.
- История честная. Перенос, исправление записи и отмена выполнения сохраняются в журнале событий.
- Пользователь управляет расписанием. Система предлагает изменения, но не переносит обязательства молча.
- Все данные закрыты по умолчанию. Публичные профили, рейтинги, подтверждения и социальные публикации включаются отдельно.
- Любое число объяснимо: пользователь может увидеть источник XP, способ расчёта графика и условие достижения.
- Нет экранов-пустышек в готовом релизе. Кнопка должна выполнять действие; недоступная возможность скрыта или явно отключена с объяснением.

### 1.3. Что означает «без ИИ»

Обычный REST API между Next.js и Go **нужен**: через него сайт сохраняет задачи и получает данные. Это не API нейросети.

| Ранее предложенная функция | Реализация в этом ТЗ |
|---|---|
| AI Coach | «Навигатор дисциплины»: правила, триггеры, готовые объяснения и шаблоны действий |
| Генерация плана цели | Каталог редактируемых шаблонов и пошаговый конструктор цели |
| Smart Scheduling | Поиск свободных интервалов и детерминированная сортировка задач |
| Daily / Weekly Quests | Выбор подходящих заданий из подготовленного каталога |
| Персональные рекомендации | Условия вида «если задача переносилась три раза — предложить дробление» |
| Future Self | Арифметический сценарий по накопленному темпу без обещания результата обучения |
| Еженедельный отчёт | Агрегация записей и подстановка данных в фиксированный текстовый шаблон |

Нельзя добавлять поля `OPENAI_API_KEY`, `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`, зависимость от Ollama и скрытые обращения к AI-провайдерам.

### 1.4. Релизы и полнота

| Релиз | Этапы | Назначение |

## 2. Пользователи и основные сценарии

### 2.1. Роли

| Роль | Разрешения |
|---|---|
| Гость | Лендинг, регистрация, вход, восстановление доступа; никакого доступа к частным данным |
| Пользователь | Только собственные задачи, планы, цели, привычки, дневник, настройки и разрешённые социальные данные |
| Участник / организатор испытания | Участие либо управление конкретным испытанием; не администратор чужого аккаунта |
| Модератор | Публичный каталог, жалобы, блокировка публичного контента; без просмотра частного дневника и токенов интеграций |
| Администратор | Управление системным каталогом, конфигурацией и служебной диагностикой; действия журналируются, общего интерфейса чтения приватных записей нет |

Системная роль и роль в испытании хранятся отдельно. Создатель испытания не может редактировать личные задачи участника.

### 2.2. Основные пользовательские истории

**US01 — первый день.** Зарегистрироваться, выбрать часовой пояс, направления жизни, создать цель, добавить две задачи и одну привычку, распределить задачи по календарю и увидеть персональный Dashboard.

**US02 — выполнение.** Открыть задачу, начать фокус-сессию, завершить работу и подтвердить результат. Задача, цель, календарь, XP и аналитика должны согласованно обновиться.

**US03 — не успел.** Перенести задачу с причиной. Исходный план остаётся в истории, будущая дата появляется в календаре, XP не начисляется.

**US04 — восстановление.** Вернуться после перерыва, включить облегчённый план и пройти небольшой Comeback Challenge без необходимости «отрабатывать» пропуски.

**US05 — долгосрочная цель.** Создать сезон «90 дней до стажировки», выбрать этапы и метрики, связать задачи и привычки, выбрать Boss of the Month.

**US06 — анализ.** Посмотреть месяц, открыть конкретную точку графика и проверить список записей, из которых она получилась.

**US07 — совместная дисциплина.** Пригласить друга в испытание, явно выбрать общие метрики, видеть только согласованную сводку и в любой момент закрыть доступ.

**US08 — управление своими данными.** Экспортировать данные, отключить интеграции, завершить все сессии и удалить аккаунт через подтверждённую процедуру.

### 3.2. Визуальный стиль

Предлагаемый стиль — взрослый dark-mode SaaS с аккуратными RPG-элементами: графитовый фон, фиолетовые и синие акценты, понятные карточки и умеренная анимация. Это проектное решение, а не требование использовать конкретный платный набор ресурсов.

Обязательны: тёмная и светлая темы; состояние системной темы; читаемые подписи; цвет плюс иконка / текст для статусов; клавиатурная навигация; заметный focus-ring; режим уменьшенного движения; возможность отключить игровые эффекты и звуки. Персонаж собирается из локального каталога лицензированных или собственных ресурсов — без генерации ИИ.

Для каждого экрана предусмотреть `loading`, `empty`, `error`, `success`, `unauthorized`, а для записывающих действий — `saving` и `conflict`. Нельзя показывать демонстрационные цифры в настоящем аккаунте.

### 3.3. Главная панель

```text
┌ Приветствие · дата · поиск · уведомления · профиль ┐
│ Уровень / XP     Daily Score     серия / восстановление │
│ Три главные задачи         │ Расписание сегодня         │
│ Привычки сегодня          │ Ближайшие дедлайны          │
│ Активное испытание        │ Прогресс главной цели       │
│ Совет по правилу          │ Короткая сводка недели      │
└ Быстро добавить · Начать фокус · Вечерний разбор ┘
```

Виджеты включаются и сортируются пользователем; порядок сохраняется. На узком экране блоки выстраиваются в одну колонку. У Dashboard единый агрегирующий API, а не десятки последовательных запросов.

<a id="features"></a>
## 4. Функциональные требования

Термины **«обязательно»**, **«должен»** и чек-листы ниже являются условиями приёмки. Для каждого F-модуля нужны серверная реализация, интерфейс, обработка ошибок и тесты. Поле на макете без работающего сохранения не считается реализацией.

### F01. Аутентификация и безопасность аккаунта

Регистрация по email и паролю, вход, выход, подтверждение email, восстановление и изменение пароля, просмотр активных сессий, завершение одной либо всех сессий. Неподтверждённый пользователь может работать с личными данными, но не публикует контент и не отправляет приглашения. Повторная отправка писем ограничена.

Пароли хешируются Argon2id. Используются короткоживущий access JWT и ротируемый случайный refresh token в защищённых HttpOnly cookies; в браузерных хранилищах токенов нет. JWT содержит `sub`, `sid`, `iss`, `aud`, `iat`, `exp`, `jti`. Сервер проверяет актуальность сессии по `sid`. Это сознательно не полностью stateless-авторизация. Детали — раздел 11 и источники S03–S05.

**Готово, когда:** повторный вход работает; неверный пароль не раскрывает сведения об аккаунте; после logout защищённый запрос отвергается; использованный reset-токен не работает повторно; два пользователя не получают чужие данные.

### F02. Профиль, онбординг и персональные настройки

Имя, ник, аватар из каталога, язык, IANA-часовой пояс, начало недели, формат времени, тема, рабочие интервалы и дни отдыха. Начальный часовой пояс предлагается из браузера; `Asia/Almaty` — пример настройки, а не жёстко заданный часовой пояс всех аккаунтов.

Пользователь выбирает направления: учёба, карьера, программирование, языки, физическая активность, личные проекты, отношения либо собственные. Можно создать до 12 активных направлений с цветом и иконкой. Онбординг предлагает создать цель, задачу и привычку, но позволяет пропустить каждый шаг.

**Готово, когда:** настройки сохраняются после перезахода, часовой пояс одинаково используется календарём и напоминаниями, повторный онбординг не создаёт дубли.

### F03. Dashboard и ежедневная сводка

Сегодняшние задачи, до трёх главных задач, привычки, ближайшие события, просрочки, уровень, XP, текущая и лучшая серия, Daily Score, активный босс, сезон и подходящая подсказка. Быстрое добавление задачи, запуск фокуса и вечерний разбор. Редактируемый состав виджетов.

**Готово, когда:** закрытие задачи обновляет все связанные карточки без перезагрузки; несуществующие данные показываются как «Пока нет данных», а не `0% дисциплины`.

### F04. Quest System — задачи

Обязательные поля: название, описание, направление, приоритет, сложность, статус, дедлайн, плановая дата, оценка длительности, теги. Дополнительно: связь с целью / этапом, подзадачи, вложения, блокирующие задачи, фактическое время, причина пропуска / переноса.

Представления: список и Kanban; поиск по тексту; фильтры по датам, направлению, статусу, цели и приоритету; сортировка; сохранённые фильтры; пакетное действие с предварительным списком затрагиваемых задач. Подзадачи глубиной до двух уровней, запрет циклических зависимостей. Шаблоны повторно используемых задач.

Действия: создать, изменить, начать, завершить, отменить выполнение, перенести, пропустить, отметить неуспех, архивировать и восстановить. Вложения: изображения PNG/JPEG/WebP, PDF и TXT; до 10 МБ за файл, до 5 файлов на запись и до 250 МБ на аккаунт по стартовой конфигурации.

**Готово, когда:** завершение сохраняется после обновления страницы, даёт награду ровно один раз; перенос оставляет историю; конкурентное редактирование не затирает изменения; чужие вложения недоступны.

### F05. Goals — цели и этапы

Цель содержит название, мотив, направление, начальную и целевую даты, критерий успеха, этапы, прогресс и историю изменений. Виды прогресса: чек-лист этапов, числовая метрика или связанные задачи. Тип расчёта выбирается явно; несопоставимые метрики не складываются в одно число.

Числовой пример: прочитать 12 книг; журнал добавляет значения с единицей «книги». Пример по этапам: создать резюме → закончить проект → отправить согласованное число откликов. Есть шаблоны «Английская практика», «Подготовка к экзамену», «Поиск стажировки», «Личный проект», но шаблон не гарантирует достижение уровня языка или трудоустройство.

Разделы: активные, приостановленные, достигнутые, завершённые без достижения, отменённые, архив. Просроченность отображается отдельно. Отчёт по недостигнутой цели: что выполнено, какие препятствия, продолжить с новой датой / пересобрать / завершить без достижения.

**Готово, когда:** прогресс вычисляется из источников, отмена выполнения его корректирует; истечение срока не делает цель автоматически проваленной; можно просмотреть и достигнутые, и недостигнутые цели.

### F06. Календарь, повторы и time blocking

Режимы день / неделя / месяц / год / список. Задачи без времени показываются в секции дня, события и временные блоки — на сетке. Drag & drop и изменение длины блока имеют альтернативу через форму. Цвета направлений, фильтры, дедлайны, индикаторы завершения, пропуска и переноса.

Повторы: ежедневно, выбранные дни недели, раз в N недель, ежемесячно по числу; конец по дате либо числу повторов. Для изменения серии — «только это повторение» или «это и будущие». Завершённая история не переписывается. На 31-е число в коротком месяце событие пропускается; интерфейс заранее объясняет правило.

Одна задача может иметь несколько блоков работы. Дедлайн и начало работы — разные поля. Внешние read-only события не превращаются в задачи автоматически. Конфликт расписания показывает оба пересекающихся блока и оставляет выбор пользователю.

**Готово, когда:** перенос в календаре изменяет ту же задачу, что отображается в списке; годовой вид работает без Premium Scheduler; переход месяца, високосный день и смена часового пояса покрыты тестами. Использовать Standard-возможности FullCalendar, проверив совместимость выбранной версии [S02, S06].

### F07. План дня и недели

Пользователь задаёт доступное время, выбирает до трёх главных задач, распределяет временные блоки и подтверждает план. До подтверждения это черновик. После подтверждения сохраняется исходный снимок для аналитики, дальнейшие изменения идут как дополнения, а не скрытая замена истории.

Шаблоны «учебный день», «рабочий день», «выходной», «идеальная неделя» содержат интервалы и действия. Применение всегда показывает предпросмотр и не дублирует уже добавленные элементы. Невместившиеся задачи остаются отдельным списком.

**Готово, когда:** можно составить, подтвердить и пересмотреть план; система показывает запланированные минуты и доступную ёмкость; удаление задачи после подтверждения не повышает старую оценку выполнения задним числом.

### F08. Habit Tracker

Типы привычек: бинарная, количественная, по длительности. Расписание: каждый день, конкретные дни, N выполнений в неделю, N выполнений в месяц. У каждой привычки есть цель периода, минимальный шаг, направление, даты действия, архивирование и необязательные напоминания.

Отметка хранит количество и время, а не только boolean. Количественная норма: например 20 страниц; 10 страниц дают 50% прогресса периода, но не полную награду. «Три раза в неделю» оценивается за неделю, а не как семь обязательных ежедневных выполнений.

Показывать текущую и лучшую серию, долю успешных запланированных периодов, историю исправлений. Предусмотреть плановую паузу и отдых. Нельзя переписывать расписание прошлого, чтобы скрыть пропуски.

**Готово, когда:** несколько отметок за период суммируются без двойной награды; незапланированные дни не ломают серию; недельная привычка не считается проваленной в понедельник.

### F09. XP, уровни и прозрачная история наград

Опыт выдаётся сервером по версии правил, записывается в неизменяемый журнал и связан с конкретным источником. Есть общий уровень, прогресс до следующего, история начислений, объяснение ограничения и корректировки ошибочного выполнения.

За создание задач, перенос, просмотр страницы, сон браузерной вкладки и простое количество коммитов опыта нет. Ограничения на мелкие задачи и защита от двойных запросов обязательны. Полная таблица и формулы — раздел 6.

**Готово, когда:** повтор одинакового запроса не выдаёт новую награду; работа из двух вкладок даёт один результат; баланс восстанавливается из журнала.

### F10. Персонаж, направления и Skill Tree

Персонаж собирается из слотов: базовый образ, одежда, головной убор, аксессуар, фон и рамка профиля. Есть бесплатный стартовый набор; новые предметы открываются за уровень, достижения или игровые монеты. Все предметы косметические.

Дерево навыков привязано к направлениям жизни. Выполнение конкретной задачи или привычки прокачивает одно выбранное направление. Узлы имеют прозрачные условия: уровень направления, определённое число периодов или достижение. Названия характеристик описывают активность в приложении, а не реальный интеллект, здоровье или профессиональную квалификацию.

**Готово, когда:** нельзя надеть не принадлежащий аккаунту предмет; предмет сохраняется в профиле; XP направления не добавляет повторно общий XP; условие каждого узла видно.

### F11. Achievements, титулы и личные рекорды

Каталог минимум из 30 достижений: первая задача, первая цель, 7/30 успешных периодов привычки, 10/50 фокус-сессий, завершённый сезон, Comeback, совместное испытание. Конкретные определения хранятся в версионируемом каталоге.

Титулы за уровни и отдельные действия; пользователь выбирает отображаемый титул. Рекорды: лучшая серия, самая длинная подтверждённая фокус-сессия в допустимом диапазоне, выполненные важные задачи, недельная регулярность. Нет наград за опасные или чрезмерные нагрузки.

**Готово, когда:** достижение выдаётся единожды при выполнении условия; экран показывает прогресс и правило; массовый пересчёт не создаёт дубликаты.

### F12. Coins и Reward Shop

Виртуальные монеты выдаются вместе с допустимым XP. Магазин содержит косметику и собственные реальные награды пользователя: например «вечер игры» или «поход в кино». Пользователь сам определяет описание и стоимость реальной награды. Сайт не покупает товары и не оплачивает услуги.

У покупки есть состояния: создана / получена / отменена, где отмена разрешена только для ещё не полученной личной реальной награды. Косметика выдаётся атомарно и не продаётся повторно, если предмет уже есть. Отдельная история поступлений, покупок и возвратов.

**Готово, когда:** невозможно потратить один баланс дважды; повтор запроса не списывает монеты повторно; отказ из-за нехватки баланса не меняет данные.

### F13. Boss Battles и Boss of the Month

Босс — визуальное представление большой цели с обязательными этапами. HP отражает оставшуюся долю плана; это не самостоятельная задача с дополнительным XP. Завершение этапов наносит «урон», отмена выполнения возвращает соответствующую долю HP.

Пользователь выбирает до одного главного босса месяца. Можно приостановить бой, изменить будущие этапы с записью версии, закончить без победы и вернуться к цели позже. Победа даёт косметическую награду / титул, но не удваивает XP всех вложенных задач.

**Готово, когда:** HP согласован с источниками, босс не побеждён до выполнения обязательных условий, перенос месяца не удаляет историю.

### F14. Daily / Weekly Quests и Challenges

Каталог системных заданий и конструктор собственных испытаний. Типы: ежедневные, еженедельные, накопительные, заданное число успешных периодов, завершение этапов. Примеры: 30 периодов английской практики, 10 часов фокуса, 7 вечерних разборов. Числа редактируются в допустимых пределах.

В испытании фиксируются: цель, единица измерения, источник записей, диапазон дат, часовой пояс, допустимые пропуски, способ подтверждения, видимость и награда. После старта правила соревнования не меняются; новая редакция — отдельный запуск.

Прогресс может строиться из задач / привычек / фокуса либо ручных отметок, но один источник не считается дважды внутри одной метрики. Предложение системного квеста само по себе не добавляет обязательство в план.

**Готово, когда:** участник видит правила до вступления; после достижения результата выдаётся одна награда; достижение конца срока корректно завершает испытание; можно выйти без публикации причины.

### F15. Personal Seasons

Сезон длиной 30, 60, 90 дней либо пользовательского диапазона до 365 дней. Есть тема, главный результат, связанные цели, испытания и этапы. В один момент допускается один основной личный сезон; архив не ограничивает просмотр истории.

На странице: дни до конца, прогресс по отдельным целям, выполненные этапы, награды и итоговый отчёт. Достигнутые ранее уровни не сбрасываются при начале сезона. Сезонные рейтинги применяются только к явно присоединённым публичным сезонам.

**Готово, когда:** завершение сезона фиксирует снимок, новый сезон не удаляет старые результаты, досрочное завершение требует подтверждения и причины.

### F16. Mystery Rewards

Редкие косметические сюрпризы за определённые достижения и конец сезона. Без покупки за настоящие деньги, платных случайных наборов и необходимости бесконечно обновлять страницу.

При событии награда один раз выбирается серверным генератором из допустимого набора с опубликованными весами. Результат записывается до показа; повтор открытия возвращает тот же предмет. Предпочтение предметам, которых нет; при полном наборе — заранее установленная небольшая компенсация монетами с отдельным ключом начисления.

**Готово, когда:** повторный запрос не перебрасывает награду; каталог объясняет состав и вероятности; функциональность можно отключить без потери основных наград.

### F17. Focus Mode и старт на пять минут

Pomodoro и свободная сессия. Настройки рабочих / перерывных интервалов; старт, пауза, продолжение, завершение, отмена; привязка к задаче и цели. После завершения — короткое подтверждение результата и комментарий. Фокус учитывается в минутах, но сам таймер не доказывает полезную работу.

Кнопка «Начать с пяти минут» создаёт короткую сессию для выбранной задачи. После неё можно закончить без штрафа либо продолжить. Одновременно допускается одна активная сессия на аккаунт. Перезагрузка страницы восстанавливает её по серверным временным отметкам; паузы не считаются работой.

Стартовые пределы: рабочий Pomodoro-интервал 5–120 минут, перерыв 1–60 минут; свободная сессия — максимум 4 часа активного времени и 8 часов от первого старта. При достижении предела сервер ограничивает засчитываемый интервал и переводит сессию в состояние ожидания завершения; дальнейшее время не прибавляется. Продолжение работы — новая сессия после закрытия текущей. Фактическое время задачи выбирается в режиме `from_focus` либо `manual_override`: ручная оценка заменяет итог для задачи, а не прибавляется поверх тех же фокус-сессий. В аналитике источник и факт переопределения видны; история фокуса при этом не удаляется.

**Готово, когда:** два устройства не запускают параллельные таймеры; сон вкладки не увеличивает точность подсчёта искусственно; сессия не завершает задачу автоматически и не даёт второй XP за ту же работу.

### F18. Дневник, утро, вечер и Weekly Reset

Частный дневник с заголовком, текстом, тегами и привязкой к дате / цели. Morning Routine: оценить доступное время, выбрать главные задачи, подтвердить план. Evening Review: выполнено / перенесено / препятствия / один вывод. Weekly Reset: разобрать хвосты, архивировать неактуальное, выбрать приоритеты следующей недели.

Ритуалы используют редактируемые чек-листы и сохраняют черновики. Энергия и настроение — необязательная субъективная отметка, без медицинских интерпретаций. Повторный разбор одного дня редактирует запись, а не создаёт дубликат для накрутки.

**Готово, когда:** дневник виден только владельцу, закрытие формы предупреждает о несохранённом тексте, повторный weekly reset не дублирует задачи.

### F19. Аналитика, графики и Life Balance Radar

Графики по 7 / 30 / 90 дням, году и выбранному диапазону: выполненные / невыполненные задачи, своевременность, переносы, целевой прогресс, привычки, активный фокус, плановое и фактическое время, категории деятельности и источники XP. Heatmap дня и года; сравнение соседних равных периодов; drill-down к исходным записям.

Life Balance Radar строится как выполнение **лично заданных ориентиров** по направлениям. Если ориентир не задан, значение неизвестно. Radar не оценивает качество отношений, здоровье и ценность человека. Табличная альтернатива каждому графику обязательна.

Метрики Daily Score, Discipline Score и Future Self определены ниже. Автоматический недельный / месячный отчёт — готовый текстовый шаблон со ссылками на данные. Личные рекорды F11 отображаются здесь же.

**Готово, когда:** контрольная выборка даёт ожидаемые числа, отсутствие данных не заменяется нулями, сравнение показывает абсолютную разницу при нулевой базе, графики учитывают пользовательский часовой пояс.

### F20. Навигатор дисциплины без ИИ

Правила наблюдают за переносами, перегрузкой плана, короткой серией, пропусками и приближающимися сроками. Каждая карточка содержит условие, использованные числа, короткий текст и понятное действие: открыть задачу, разбить, выбрать слот, включить облегчённый режим, пересмотреть привычку.

Пользователь может скрыть подсказку, отключить правило или отложить его. Подсказки не читают произвольный текст дневника: для правил используются только согласованные структурированные поля.

**Готово, когда:** одинаковые входные данные и версия правил дают одинаковую рекомендацию; без внешней сети подсистема продолжает работать; изменение данных происходит только после подтверждения.

### F21. Smart Scheduling и Deadline Radar

Алгоритм ищет подходящие свободные интервалы с учётом расписания, длительности, дедлайна, приоритета, зависимостей, перерывов и режима энергии. Задача без оценки времени сначала требует оценки. Если места нет — явно показать дефицит, а не вставлять пересечение.

Deadline Radar группирует: просрочено, менее суток, до трёх дней, до недели. Он показывает оставшиеся обязательные задачи и сравнивает оценку работы со свободным временем. Никаких «87% вероятности провала» без соответствующей модели: только арифметические предупреждения.

**Готово, когда:** предложение не меняет календарь до согласия, занятое событие блокирует интервал, устаревший план нельзя применить поверх новой записи без пересчёта.

### F22. Recovery Mode, Comeback и Low-Energy Mode

Recovery предлагает небольшой возврат после перерыва; Comeback — отдельное короткое испытание. Low-Energy сокращает **предлагаемый будущий план** до выбранного минимального объёма. Важные фиксированные обязательства не удаляются: показываются отдельно и требуют осознанного решения.

Плановый отдых не является успешным выполнением, но не ломает серию запланированных периодов. Нельзя «купить» исправление истории. После реального пропуска текущая серия начинается заново, лучшая сохраняется; отдельный индикатор восстановления показывает возврат без подмены цифр.

**Готово, когда:** включение режима не переписывает вчерашние показатели, есть предпросмотр изменения плана, сообщения не стыдят пользователя.

### F23. Друзья и Accountability Partners

Приглашения, принятие / отклонение, удаление, блокировка; возможность выбрать партнёра по дисциплине. До подтверждения обеими сторонами доступ не появляется. Отдельно разрешаются: общая регулярность, прогресс конкретного испытания, отметка вечернего разбора. Тексты дневника и названия частных задач не передаются.

Партнёр может отправить ограниченное число дружелюбных напоминаний по шаблону; пользователь может отключить их. Общая лента содержит только явно опубликованные достижения. Открытого чата в первом полном релизе нет.

**Готово, когда:** удаление или блокировка сразу закрывают доступ; нельзя подписаться на чужую статистику по подбору ID; есть ограничение спама и жалоба.

### F24. Co-op, PvP и глобальные испытания

Совместный вызов имеет общую цель; PvP — одинаковую метрику, период, единицу и лимиты для обеих сторон. Сравнивать произвольный личный XP людей с разными задачами нельзя. До участия видно, какие результаты самоотчётные и какие подтверждены партнёром либо интеграцией.

Рейтинги включаются отдельно; ник вместо email; ничья допустима. Организатор не видит приватные исходные задачи. Можно прикрепить разрешённое доказательство, но нет обещания полностью исключить накрутку. Спорные записи помечаются, а не удаляются без журнала.

**Готово, когда:** правила фиксируются на старте, повтор события не увеличивает счёт, удалённый участник и скрытый профиль корректно отображаются, награда за итог выдаётся один раз.

### F25. Уведомления

Центр уведомлений в приложении; напоминания по времени, дедлайны, привычки, приглашения, достижения, отчёты. Email — по включённой настройке, браузерные push — после запроса разрешения по действию пользователя. Должен быть рабочий in-app канал даже при недоступности email / push.

Настройки по типу и каналу, тихие часы, snooze, частотные ограничения и отметка прочитанного. Перенос задачи отменяет старое напоминание. Для внешних каналов предусмотрены повторная попытка и отображение состояния доставки.

**Готово, когда:** одно событие не создаёт десятки уведомлений, устаревшие напоминания не отправляются, отказ браузера в push не ломает сайт.

### F26. Интеграции и календарный обмен

**Google Calendar:** явно выбрать календарь для чтения занятости; импортировать события как read-only блоки. По отдельному согласию — экспорт выбранных задач в отдельный календарь ASCEND. Не удалять и не менять чужие события. Права подключения должны соответствовать выбранному действию.

**GitHub:** подключить выбранные репозитории через GitHub App, получать разрешённые события issue / pull request, связывать их с задачами. Закрытый issue или merged PR может предложить завершить связанную задачу. Автовыполнение допускается только для заранее настроенной связи и включённого правила; награда идёт через общий механизм. Количество коммитов не является источником XP.

**ICS:** скачать календарь выбранного диапазона; импортировать ограниченный поддерживаемый набор событий с предпросмотром и защитой от дублей. Неподдерживаемые правила не интерпретировать приблизительно: показать предупреждение.

**Готово, когда:** отключение интеграции отзывает локальный доступ и останавливает задания; сбой провайдера не ломает личный календарь; повтор sync / webhook не создаёт дубликаты [S07–S10].

### F27. Поиск, переносимость и управление данными

Глобальный поиск по своим задачам, целям и заметкам с фильтрами. Отдельное включение заметок в выдаче на общих устройствах. Экспорт полного личного архива JSON + CSV по основным сущностям; ZIP вложений по явному выбору. Импорт собственного экспортного формата с проверкой версии, предпросмотром, режимом dry run и отчётом об ошибках.

Удаление аккаунта через повторное подтверждение пароля / свежей сессии, отключение интеграций, немедленное прекращение доступа и фоновое удаление данных по описанной политике. Приватные данные не должны оставаться в чужих социальных карточках.

**Готово, когда:** экспорт принадлежит только владельцу; импорт не позволяет передать `owner_id` другого аккаунта и не накручивает XP; после удаления аккаунт не доступен, а задача очистки имеет проверяемый результат.

### F28. Каталоги, модерация и системные настройки

Минимальная служебная панель: подготовленные шаблоны целей и заданий, каталоги достижений / косметики, глобальные испытания, просмотр жалоб, блокировка публичного контента, версия правил наград. Предпросмотр изменений; опубликованная версия правил не редактируется задним числом.

Администратор не может одной кнопкой произвольно увеличить баланс пользователя. Исправление ошибочного начисления — отдельная аудируемая операция с причиной. Секреты интеграций не выдаются через панель.

**Готово, когда:** пользователь без роли получает отказ API, изменения каталогов записаны в аудит, переключение версии правил не меняет уже выданные награды.

<a id="domain"></a>
## 5. Правила данных и состояний

### 5.1. Время, даты и часовые пояса

1. Момент времени (`created_at`, `completed_at`, начало timed-события) хранить в PostgreSQL как `timestamptz`; API передаёт ISO 8601 с UTC `Z` или явным смещением.
2. Дата без времени (`planned_date`, день отдыха, all-day событие) хранится как `date`, а не «полночь UTC». Для all-day конца использовать исключающую границу: событие на 12 октября имеет конец 13 октября.
3. Правило повтора содержит IANA-часовой пояс и локальное время начала. Это позволяет повторять «09:00 по выбранному поясу», а не фиксированное время UTC.
4. У привычки, плана дня и запуска испытания сохранять часовой пояс расчёта. При смене профиля прошлые периоды не пересобирать; изменения затрагивают будущие периоды после показанного пользователю предпросмотра.
5. Для зон с переходами времени: отсутствующее локальное время переносится вперёд на величину скачка; при двукратном времени выбирать первое вхождение. Отображать предупреждение; закрепить поведение тестами адаптера времени.
6. Обязательные тесты: `Asia/Almaty`, `UTC` и зона с сезонными переходами. Использовать внедряемый `Clock`, не вызывать текущее время напрямую из доменной логики.
7. Историческое завершение можно исправить вручную с причиной и журналом. Запись помечается `backfilled`; не получает соревновательный зачёт за закрытый период. XP за задачу привязан к реальному моменту принятия завершения сервером, а не произвольной пользовательской дате.

### 5.2. Состояния задачи

| Статус | Значение |
|---|---|
| `backlog` | Идея / задача ещё не взята в план |
| `todo` | Готова к выполнению |
| `in_progress` | Выполняется |
| `postponed` | Перенесена на другую дату; остаётся открытой |
| `completed` | Выполнена |
| `failed` | Пользователь явно зафиксировал неуспешный результат |
| `skipped` | Пользователь решил пропустить этот экземпляр |

`overdue` — вычисляемый признак открытой задачи с прошедшим дедлайном, а не статус. `archived_at` — отдельный признак архивирования; не уничтожает фактический итог.

Допустимые переходы:

```text
backlog → todo / in_progress / completed / skipped / failed
 todo → in_progress / completed / postponed / skipped / failed
postponed → todo / in_progress / completed / postponed / skipped / failed
in_progress → todo / completed / postponed / skipped / failed
completed → todo  (reopen + корректировка награды)
failed / skipped → todo  (reopen + сохранение исходного события)
```

Перенос требует новой плановой даты либо явного «вернуть в backlog», причины и `version`. Дедлайн сам не сдвигается: для его изменения нужен отдельный флаг с подтверждением. Автоматическое истечение дедлайна не переводит задачу в `failed`.

### 5.3. Дерево задач, этапы и зависимости

- Запрет родительства самому себе, циклов и глубины выше двух уровней подзадач.
- Листовая задача может получать XP. Контейнер с дочерними задачами показывает сводный прогресс и не получает дополнительную награду за завершение.
- Для задачи, уже получившей XP, добавление подзадач требует сначала отменить выполнение. При превращении в контейнер старое entitlement закрывается и не может быть восстановлено как листовая награда без возврата структуры; UI показывает последствия.
- Родитель считается выполненным после выполнения всех обязательных листьев. Ручное закрытие родителя не закрывает детей молча.
- Вес листа фиксируется в версии плана; по умолчанию 1. Пользователь может задать веса этапов; сумма нормализуется при расчёте.
- Зависимость A → B означает: B нельзя начать до завершения A. Пропуск A не считается выполнением зависимости. Пользователь должен явно снять / изменить блокировку с записью в истории.

### 5.4. Цели и прогресс

Статусы: `draft`, `active`, `paused`, `achieved`, `not_achieved`, `cancelled`. Архивирование отдельно. Достигнутый числовой порог создаёт предложение подтвердить цель; пользователь подтверждает либо фиксирует дополнительный обязательный критерий.

Для цели с задачами:

```text
progress = 100 × sum(weight выполненных обязательных листьев)
                 / sum(weight всех обязательных листьев)
```

Для числовой цели при `target > start`:

```text
progress = clamp((current - start) / (target - start), 0, 1) × 100
```

В первом релизе числовые цели только возрастающие: «накопить N действий / минут / единиц». Уменьшение веса, медицинские показатели и другие показатели с обратным направлением не поддерживаются приблизительным расчётом.

Для нескольких ключевых результатов показывать каждый отдельно. Сводный процент разрешён только через заранее заданные веса нормализованных результатов. Изменение целевого значения после начала сохраняет старую и новую версии.

Если именно исправление исходной записи снижает ранее подтверждённую цель ниже обязательного порога, записать `goal.achievement_reverted`, вернуть цель в `active` и показать объяснение владельцу. Это не штраф за новый пропуск: корректируется прежний неверный результат. Связанные производные достижения и HP пересчитываются. Снимок уже закрытого сезона не переписывается бесследно: к нему добавляется запись корректировки; первоначальный и исправленный итоги различимы. Исправления закрытого соревновательного периода проходят установленный при запуске срок рассмотрения и помечаются в истории, а не добавляют задним числом новую победу.

### 5.5. Привычки и серия

Единица серии — **запланированный период**, не всегда календарный день. Для привычки по понедельникам / средам / пятницам следующий вторник не является пропуском. Для «3 раза в неделю» успешный период — завершённая неделя с тремя отметками.

`current_streak` — число последовательных закрытых успешных запланированных периодов; текущий незавершённый период не ломает серию. При достижении нормы текущий период можно учитывать как успешный один раз. `best_streak` — максимум по журналу с учётом корректировок; не просто растущий счётчик без возможности пересчёта ошибки.

Пауза / отдых могут исключать только ещё не начавшиеся периоды. Экстренную паузу в уже начавшемся периоде можно записать как уважительную причину, но не как успешное выполнение. Разрешённые дни отдыха не дают XP и не создают фиктивные успешные дни.

### 5.6. Повторяющиеся задачи и события

`recurrence_series` хранит правило; `task_occurrences` / `calendar_occurrences` — конкретный экземпляр с уникальным ключом `(series_id, occurrence_key)`. Сервер создаёт экземпляры при запросе диапазона и фоновым пополнением горизонта до 60 дней. Один запрос может материализовать не более 400 экземпляров.

Отмена повторения создаёт исключение, а не удаляет правило. Изменение «это и будущие» завершает старую серию перед выбранным экземпляром и создаёт новую. Завершённые экземпляры, использованные планы и начисления не мигрируют на новую серию.

Для повторяемой задачи награда привязана к экземпляру, а не всей серии. Если создана задача по шаблону привычки, её необходимо связать с тем же источником выполнения либо отключить вторую награду. Одно и то же действие не маскируется под две записи для удвоения опыта.

### 5.7. Удаление и история

Частные рабочие сущности сначала архивируются / мягко удаляются на 30 дней с возможностью восстановления. Публичные карточки скрываются сразу. После срока фоновая очистка удаляет содержимое; ссылки в собственных исторических сводках заменяются минимальной записью «удалённый объект».

Журнал игровой экономики остаётся достаточным для пересчёта баланса без хранения названия задачи. При удалении аккаунта удаляется и его личный журнал; в общих испытаниях остаётся только обезличенный необходимый итог. Конкретные сроки резервных копий — раздел 18.

## 6. Игровая экономика и формулы

Все числа ниже — **стартовые настройки дизайна продукта**, а не научно установленные показатели дисциплины. Хранить их в версионируемой конфигурации. Изменения применяются к новым правам на награду, не пересчитывают старые произвольно.

### 6.1. XP и ограничения

| Источник | Базовый XP | Ограничение |
|---|---:|---|
| Листовая задача `micro` | 5 | Общая квота задач |
| Листовая задача `easy` | 10 | Общая квота задач |
| Листовая задача `medium` | 25 | Общая квота задач |
| Листовая задача `hard` | 50 | Общая квота задач |
| Листовая задача `epic` | 100 | Общая квота задач; рекомендовать разбиение |
| Привычка: полностью достигнута норма периода | 10 | Один раз за период |
| Завершение пользовательского / системного испытания | 25 | Один раз за запуск на участника |
| Фокус-таймер сам по себе | 0 | Минуты учитываются для аналитики и испытаний |
| Цель, этап-контейнер, босс, достижение, открытие страницы | 0 | Отдельные косметические награды возможны |

Квоты за **скользящие 24 часа по серверному времени**: задачи — 200 XP, привычки — 50 XP, испытания — 50 XP. Совокупно не более 300 XP из этих источников. Смена часового пояса не обнуляет квоты.

При превышении квоты выдаётся оставшийся допустимый XP, вплоть до 0, с объяснением. Выполнение и прогресс засчитываются полностью. Остаток XP не копится «на завтра». Это снижает возможности фарма, но не является доказательством реального выполнения.

Для исторической отметки привычки: награда допустима, если отметка принята до конца периода + 24 часа; позже история корректируется без новой награды. Для соревнования действуют собственные фиксированные сроки, не более строгие скрытым образом.

### 6.2. Уровни и титулы

```text
XP_threshold(level) = 100 × (level - 1)², level >= 1
level(total_xp) = floor(sqrt(max(total_xp, 0) / 100)) + 1
xp_inside_level = total_xp - XP_threshold(level)
xp_to_next = XP_threshold(level + 1) - total_xp
```

Контрольные значения: XP 0 → уровень 1; 99 → 1; 100 → 2; 399 → 2; 400 → 3; 900 → 4. В коде избегать ошибки floating-point на границе; вычислять уровень через целочисленную проверку порога.

Титулы по умолчанию: уровни 1–4 Beginner, 5–9 Apprentice, 10–19 Disciple, 20–34 Warrior, 35–49 Master, 50+ Legend. В UI — локализованные подписи. Отдельные титулы достижений не изменяют права доступа или заработок.

### 6.3. Монеты и корректировки

Обычное начисление монет: `coins = floor(awarded_xp / 5)`. За XP 25 — 5 монет. За награду, уменьшенную квотой до 3 XP, — 0 монет. Стартовая бесплатная косметика не зависит от этой формулы.

Каждое первое выполнение создаёт `reward_entitlement`: источник, снимок сложности, версия правил, исходный размер, фактически выданный XP / coins, `first_awarded_at`. Повтор запроса возвращает существующий результат. Редактирование сложности после завершения не повышает старую награду.

При отмене выполнения создаётся компенсирующая запись на исходные суммы, а не удаление журнала. Повторное завершение того же логического экземпляра восстанавливает только исходное entitlement, не создаёт новое право и не потребляет квоту второй раз. Компенсация **не освобождает уже использованную квоту** первых начислений в скользящем окне.

Если монеты уже потрачены, отмена ошибочного выполнения может сделать расчётный баланс отрицательным. UI отдельно показывает «доступно: 0» и «корректировка: N виртуальных монет»; это не денежный долг. Новые монеты сначала закрывают корректировку; новые покупки запрещены до достаточного баланса. Пропуск задач сам по себе такую корректировку не создаёт.

### 6.4. Атомарность и защита от повторов

Обработка завершения задачи в одной транзакции:

```text
1. Проверить сессию и принадлежность задачи пользователю.
2. Найти завершённую операцию по idempotency key и hash тела; при совпадении вернуть
   сохранённый результат до повторной проверки уже изменившейся version.
3. В транзакции захватить блокировки в порядке user_progress → task → entitlement,
   повторно проверить ключ при конкуренции, затем статус, зависимости и version.
4. Изменить статус, записать task_event и completion_id.
5. Рассчитать / восстановить entitlement по версии правил и квотам.
6. Добавить записи XP / coins и обновить проекцию баланса.
7. Добавить outbox-событие для достижений, уведомлений и статистики.
8. Зафиксировать транзакцию и вернуть фактические суммы.
```

Если шаг упал — изменения откатываются целиком. Постобработка из outbox может повторяться; все потребители идемпотентны. `SELECT ... FOR UPDATE`, уникальные ограничения и повтор транзакции при обнаруженном конфликте используются осознанно; поведение блокировок проверяется по документации PostgreSQL [S11].

Покупка награды блокирует строку баланса, проверяет доступную сумму, списывает монеты и выдаёт предмет / создаёт redemption в одной транзакции. Нельзя выполнять «прочитать баланс → отдельно списать» без блокировки.

### 6.5. Daily Score

За подтверждённый день:

- `T` — доля выполненных запланированных листовых задач с весами приоритета: низкий 1, обычный 2, высокий 3.
- `H` — средняя доля выполнения норм привычек, обязательных в этот день / закрывающийся период, с ограничением каждого значения до 1.
- У задач учитывается снимок подтверждённого плана и своевременное выполнение в этом дне. Внеплановые выполненные задачи видны отдельно и не исправляют невыполнение другой задачи.

```text
DailyScore = round(100 × (0.6 × T + 0.4 × H) / active_weight_sum)
```

Неактивный компонент исключается и из числителя, и из знаменателя. Нет задач и привычек → `null`, надпись «Нет плана», не 0 и не 100. Только задачи → `100 × T`. Плановый день отдыха → «Отдых», без оценки.

Пример: две задачи с весами 3 и 1, выполнена только первая → T = 0.75. Привычки выполнены в среднем на 0.5 → Daily Score = 65.

### 6.6. Discipline Score

Это показатель выполнения **собственных планов**, а не оценки личности. На экране обязательно показывать объём задач и число активных дней рядом с баллом.

Для каждого завершённого запланированного дня:

```text
R = min(1, available_minutes / planned_minutes), если planned_minutes > 0
DayDiscipline = 100 × (0.50 × T + 0.35 × H + 0.15 × R) / active_weight_sum
DisciplineScore = round(mean(DayDiscipline за последние 14 календарных дней с планом))
```

Если данных меньше трёх завершённых дней — «Недостаточно данных» и число учтённых дней. Отдых и отсутствие плана исключаются; день с подтверждённым, но невыполненным планом не исключается. `available_minutes` фиксируется при подтверждении. R отражает выполнимость объёма плана по времени, а не качество работы.

Не использовать этот показатель для публичного рейтинга. Изменения формулы требуют новой `score_version`; прошлые отчёты показывают применённую версию.

### 6.7. Future Self, сравнения и другие графики

Future Self: средний объём подтверждённой активности за последние четыре **полные** недели × выбранное число будущих недель. Учитываются и нулевые недели. Если наблюдений меньше двух полных недель — недостаточно данных. Результат: «При сохранении темпа 4 часа в неделю за 12 недель добавится около 48 часов практики». Нельзя превращать часы в обещание B2, работы или физического результата.

Сравнение периодов: если предыдущая величина > 0, относительное изменение `(current - previous) / previous × 100`; при нулевой базе показывать абсолютную разницу без бесконечных процентов. Время фокуса хранить целыми секундами, отображаемые минуты округлять только на UI.

Life Balance Radar: `min(actual / personal_target, 1) × 100` для каждого отдельного направления и единицы. При `target <= 0` — нет ориентира. Heatmap имеет легенду и показывает конкретные значения, а не неизвестный «уровень жизни».

## 7. Автоматизация без ИИ

### 7.1. Каталог стартовых правил

| ID | Условие | Предлагаемое действие | Ограничение |
|---|---|---|---|
| R01 | Задача переносилась 3+ раза за 14 дней | Разбить на шаги / пересмотреть актуальность | Не чаще раза на задачу за 7 дней |
| R02 | Плановые минуты > доступных | Убрать необязательные блоки из будущего плана | Не менять без подтверждения |
| R03 | До дедлайна меньше суток, оценка работы больше свободных слотов | Открыть конфликт и приоритизировать | Показать конкретные минуты |
| R04 | В двух закрытых периодах привычки норма не достигнута | Предложить меньшую будущую норму | Прошлые периоды не менять |
| R05 | Нет подтверждённых действий 3 дня, пользователь вернулся | Comeback на 3 небольших шага | Не чаще раза за 14 дней |
| R06 | Пользователь выбрал низкую энергию | Предложить минимальный план | Срочные обязательства остаются видимыми |
| R07 | Открыта задача более 60 минут, нет первого шага | «Начать с 5 минут» / создать подзадачу | Время открытия само не оценивает лень |
| R08 | Завершена неделя, ещё нет обзора | Weekly Reset | Одно уведомление за неделю |
| R09 | Средняя фактическая длительность задачи данного шаблона > оценки на 50%, минимум 5 завершений | Предложить обновить оценку будущих копий | Показать выборку, не менять старые задачи |
| R10 | Есть цель без следующего действия | Добавить первую задачу из шаблона | До 3 карточек подсказок одновременно |
| R11 | Привычка выполнена 7 запланированных периодов подряд | Предложить посмотреть достижение | Не повышать норму автоматически |
| R12 | Временные блоки двух календарей пересекаются | Выбрать перенос / оставить осознанный конфликт | Не удалять внешний блок |
| R13 | Цель просрочена, но есть прогресс | Пересмотреть срок / завершить без достижения | Без ярлыка «провал» |
| R14 | Не выбран Boss of the Month | Предложить существующую активную цель | Не создавать новую цель автоматически |
| R15 | Есть неподтверждённые итоги фокуса | Разобрать сессии | Не начислять минуты в соревнование молча |

Правило хранит `id`, `version`, `priority`, `conditions`, `template_key`, `action_type`, `cooldown`, `enabled`. Выполнение — через типизированные обработчики, **не через eval / произвольный JavaScript из базы**. Админ может менять параметры и шаблон в разрешённой схеме, но не исполняемый код.

### 7.2. Алгоритм Smart Scheduling

```text
Вход: задачи, рабочие интервалы, занятые события, длительности,
      зависимости, обязательные перерывы, часовой пояс, режим дня.

1. Проверить диапазон: не более 14 дней на одну операцию.
2. Построить свободные интервалы из рабочих окон минус занятые блоки и перерывы.
3. Исключить выполненные, архивные и заблокированные задачи.
4. Отсортировать: фиксированный дедлайн ↑, приоритет ↓, дата создания ↑, id ↑.
5. Для каждой задачи найти первый подходящий слот до дедлайна.
6. Разбивать задачу на части только при allow_split=true;
   минимальный блок — 15 минут, кроме специального старта на 5 минут.
7. Вернуть placements, unscheduled, warnings, входные версии и expires_at.
8. После подтверждения повторно проверить версии и занятость.
9. Сохранить блоки атомарно; при конфликте вернуть 409 и новый предпросмотр.
```

Срок действия предложения — 10 минут. Это стартовая конфигурация. Алгоритм не обещает математически оптимальный план; контракт — повторяемый, объяснимый результат без скрытых конфликтов. Формирование расписания не изменяет дедлайны.

### 7.3. Шаблон отчёта

```text
За неделю {start}–{end}:
— выполнено {completed} из {planned} запланированных задач;
— закрыто {habit_success}/{habit_due} периодов привычек;
— подтверждено {focus_minutes} минут концентрации;
— самая частая указанная причина переноса: {reason или «не указана»};
— следующий шаг: {rule_based_action или «выберите приоритет новой недели»}.
```

В итоговом интерфейсе каждое число кликабельно до списка источников. В отчёт партнёру включаются только отдельно разрешённые поля; дневник не входит.

### 9.3. Обязательные ограничения и индексы

- `UNIQUE(owner_id, local_date)` для `day_plans` и отдельный уникальный ключ вида обзора для `daily_reviews`.
- `UNIQUE(series_id, occurrence_key)` для повторов; `UNIQUE(habit_id, period_key)` для периодов привычек.
- `UNIQUE(user_id, source_type, source_id, reward_kind)` для прав на награды; журнал поддерживает отдельные уникальные ключи операций начисления / компенсации / восстановления.
- `UNIQUE(provider, delivery_id)` для webhook inbox; `UNIQUE(connection_id, external_id)` для внешнего отображения события.
- `UNIQUE(user_id, method, route_key, idempotency_key)` для идемпотентных запросов.
- Частичный уникальный индекс на `focus_sessions(user_id)` для незакрытых `running` / `paused` / `awaiting_confirmation` сессий.
- Частичный уникальный индекс на основной активный личный сезон пользователя.
- CHECK `ends_at > starts_at`, `target > 0`, `amount >= 0`, `cost >= 0`, допустимые статусы и отсутствие отрицательного активного времени.
- Индексы задач `(owner_id, status, due_at)` и `(owner_id, planned_date)`; привычек по владельцу; ledger `(user_id, created_at)`; jobs `(state, next_run_at)`.
- Привязки между двумя частными сущностями защищены проверкой владельца; для критичных связей использовать составной FK `(owner_id, entity_id)`, а не только UUID.
- Поддерживать экспорт и удаление по `owner_id`; проверить планы запросов на контрольном объёме данных.

### 9.4. Начальные данные

Seed-каталог: минимум 8 направлений, 6 шаблонов целей, 12 шаблонов привычек, 20 шаблонов квестов, 12 испытаний, 30 достижений, 20 косметических предметов, 6 титулов уровней и правила R01–R15. Seed должен быть идемпотентным.

Демонстрационные пользователи и история доступны **только** отдельной командой для dev / test. Production seed не создаёт публичный пароль администратора. Начального администратора создавать CLI-командой с одноразовым приглашением.

<a id="api"></a>
## 10. Контракт REST API

### 10.1. Общие требования

Префикс `/api/v1`. JSON UTF-8. Контракт OpenAPI хранится в репозитории и обновляется вместе с изменением endpoint; TypeScript-типы генерируются из него. Контракт и реализация проверяются тестами. Для получения файлов допустим отдельный бинарный ответ с корректными заголовками.

Входные DTO не принимают доверенные поля `owner_id`, `awarded_xp`, `balance`, `role`, `is_admin`. Владелец берётся из сессии; вычисляемые поля — из сервиса.

Пагинация списков: `limit` от 1 до 100 и непрозрачный `cursor`; стабильная сортировка с ID как дополнительным ключом. Границы диапазона: `from` включительно, `to` исключительно; для локальных дат это указывается отдельно. Массовые изменения — максимум 50 объектов за запрос, предварительная проверка всех владельцев, атомарное выполнение.

Для изменения существующей сущности — `If-Match: "<version>"`; конфликт возвращает 409 `VERSION_CONFLICT`, актуальную версию и безопасное описание. Для завершения, покупки, отметки привычки, импорта и применения плана — `Idempotency-Key`. Один ключ с другим телом возвращает 409 `IDEMPOTENCY_MISMATCH`.

Идемпотентные ответы хранятся минимум 24 часа; критичные операции дополнительно защищены постоянным уникальным `operation_id` / entitlement. Истечение кэша ответа не должно позволять повторное списание одной операции.

### 10.2. Единый формат

```json
{
  "data": {"id": "uuid", "version": 8},
  "meta": {"request_id": "uuid", "server_time": "2026-10-12T04:10:00Z"}
}
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте поля формы",
    "fields": {"title": "Название обязательно"},
    "request_id": "uuid"
  }
}
```

Коды: 400 для некорректного JSON; 401 нет действующей сессии; 403 запрет действия по роли; 404 отсутствует или не принадлежит пользователю частный объект; 409 конфликт версии / состояния / идемпотентности; 422 корректный JSON с недопустимыми полями; 429 лимит с `Retry-After`; 500 непредвиденная ошибка без stack trace и секретов.

## 11. Безопасность и приватность

### 11.1. Пароли и сессии

Проектная политика пароля: 12–128 Unicode-символов, с ограничением входа 512 байт; разрешить пробелы и менеджеры паролей; не требовать искусственного сочетания всех классов символов. Хеш Argon2id с уникальной солью и стартовыми параметрами не ниже проверенного минимума OWASP; параметры хранить в кодированном хеше и измерить нагрузку на целевом сервере [S05].

Access JWT: 15 минут. Refresh: до 7 дней обычной сессии, до 30 дней по «Запомнить меня», с серверным абсолютным сроком. Refresh token случайный минимум 256 бит; хранить только его SHA-256-хеш, поскольку это высокоэнтропийный токен, не пароль. JWT подписывать разрешённым фиксированным алгоритмом; проверять issuer / audience / expiry / session state. Секрет подписи не является публичной frontend-переменной.

Cookies в production: `__Host-ascend_access` и `__Host-ascend_refresh`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`. Lax выбран для переходов OAuth, но не заменяет CSRF-защиту. Отдельная ограниченная dev-конфигурация допускает HTTP localhost и непредиксированные cookies; production должен отказаться запускаться с ней. Обоснование cookie-флагов и запрета токенов в web storage — S03; необходимость серверного отзыва JWT-сессий — S04.

Refresh ротируется в транзакции; повторное использование старого токена вне короткого окна конкурентного обновления отзывает семейство сессии. Для нескольких вкладок клиент координирует refresh. В течение 5 секунд после ротации повтор старого токена может вернуть только 409 `REFRESH_IN_PROGRESS`, **не новый токен**; клиент повторяет защищённый запрос с уже обновлённой cookie. При потерянном ответе и невозможности восстановить сессию требуется повторный вход. Проверить этот UX тестом.

Reset / verify токены: одноразовые случайные значения, хеш в БД, сроки 30 минут / 24 часа соответственно. Смена пароля и успешный сброс отзывают прежние сессии. Текст восстановления не раскрывает существование email.

### 11.2. CSRF, XSS, доступ и API

На каждом изменяющем браузерном запросе проверять допустимый Origin, CSRF-токен, привязанный к сессии, и Content-Type. Для login / register предусмотрен pre-auth CSRF-контекст. Безопасные GET не меняют данные. OAuth callback защищается одноразовым `state` и PKCE, а не обычным CSRF-заголовком.

Авторизация объекта проверяется на backend для каждого чтения, изменения, файла, экспорта и фонового задания. UUID не является механизмом приватности. Уведомления, кэш и поиск также разделяются по пользователю.

Санитизация отображаемого Markdown; raw HTML отключён; пользовательские URL допускают только безопасные схемы. CSP, HSTS в production, запрет MIME-sniffing, безопасные iframe / referrer-политики. SQL — параметризованный, сортировка только по allowlist полей.

### 11.3. Лимиты и файлы

Стартовые ограничения: login 5 неудачных попыток за 15 минут на пару аккаунт + IP, отдельный более высокий IP-порог; reset / resend 3 за час; приглашения 10 за сутки; партнёрские напоминания 1 на адресата за день; обычный API 120 запросов в минуту на пользователя с отдельными разумными квотами для чтения. Пороги конфигурируемые; тесты должны проверять 429 и восстановление после окна. Не блокировать весь общий кампус одним малым IP-лимитом.

Вложения проверяются по фактическому типу и расширению; лимиты из F04; имена файлов не используются как путь хранения. SVG, HTML, исполняемые форматы и архивы в обычных вложениях не разрешены. PDF/TXT отдаются как скачивание; изображения обрабатываются безопасным декодером с лимитом пикселей. Файлы хранятся вне web-root, сканируются доступным локальным антивирусным адаптером перед выдачей; при недоступном сканере в публичном production новые вложения остаются в quarantine, а не объявляются безопасными.

Архив импорта обрабатывается отдельно: защита от zip-slip, слишком большого распакованного объёма и опасного количества файлов. Максимальный JSON-импорт — 20 МБ; архив — 250 МБ в распакованном виде. Неподдерживаемые вложения пропускаются с отчётом.

### 11.4. Секреты, логи и персональные данные

`.env`, OAuth client secret, JWT secrets, refresh tokens, SMTP password и ключи облака не коммитить. `.env.example` содержит имена и безопасные пустые значения. В логах нет cookies, авторизационных заголовков, содержимого дневника и текстов reset-ссылок. Допустимы request ID, user ID в служебном защищённом контексте, код события и длительность.

OAuth refresh tokens шифруются серверным ключом с authenticated encryption и версией ключа; хранение отдельно от конфигурации шифрования. При отключении — удалить локальные токены, отозвать удалённый доступ где поддерживается, остановить jobs и скрыть кэшированные события выбранного подключения. Не уничтожать собственные задачи пользователя.

Приватный дневник исключён из административного поиска и социальных API. Перед публикацией показывать состав раскрываемых полей. Экспортные ссылки краткоживущие и требуют авторизации владельца; не отправлять приватный архив на произвольный адрес.

## 12. Фоновые задания и интеграции

### 12.1. Надёжность worker

Jobs: `pending → running → succeeded / retry_wait / dead / cancelled`. Захват через `FOR UPDATE SKIP LOCKED` и lease; падение worker после истечения lease разрешает повтор. Семантика доставки — **at least once**, поэтому каждый обработчик имеет уникальный ключ результата. Нельзя обещать сетевое «exactly once».

Повтор: экспоненциальная задержка с jitter, до 8 попыток, для провайдера — учитывать `Retry-After`. Постоянные ошибки валидации не повторять. Dead-letter отображается в служебной диагностике. Время задач — серверное; плановая дата получателя рассчитывается из сохранённой зоны.

Расписания продукта: проверка due jobs каждые 15 секунд; пополнение повторов ежедневно и по запросу диапазона; сводки после окончания локального дня; недельный отчёт после закрытия недели; ночная сверка ledger / projections; очистка по сроку хранения. Это фоновые функции **разрабатываемого приложения**, не обещание фоновой работы автора этого документа.

### 12.2. Уведомления

Уникальный `dedupe_key = user + event + channel + revision`. Перед отправкой проверить актуальность исходной задачи, согласие, тихие часы и уже совершённую доставку. В тихие часы обычное сообщение переносится на конец окна; если оно уже потеряло смысл — отменяется. Настройки допускают явное исключение для выбранного срочного дедлайна.

У email возможна ситуация «провайдер принял письмо, worker не сохранил результат»; использовать idempotency провайдера при наличии, фиксировать `delivery_unknown`, не запускать бесконечные повторения. Интерфейс не заявляет доказанную доставку, если есть только принятие провайдером.

Браузерный push не гарантирует показ пользователю в конкретную секунду. Центр уведомлений остаётся источником истории. Тихие часы через полночь и переход часового пояса тестируются отдельно.

### 12.3. Google Calendar

Запрашивать минимальные scopes по выбранной возможности: для списка календарей — `calendar.calendarlist.readonly`; чтения событий — `calendar.events.readonly`; для отдельного создаваемого календаря — `calendar.app.created`. В документе это сокращённые имена OAuth scopes; полный URI и доступность сверяются с официальной таблицей [S12]. Полный доступ `calendar` не запрашивается без отдельного обоснованного расширения требований.

Этапы синхронизации: первичная полная загрузка выбранного календаря; последующие изменения по `nextSyncToken`; обработка всех страниц перед сохранением нового токена. Ответ 410 очищает **только кэш этого внешнего источника** и запускает полную синхронизацию, не удаляет ASCEND-задачи [S07].

Push Google — сигнал о необходимости обновления, а не содержимое события. Проверять channel ID, resource ID и собственный случайный channel token; канал имеет срок и обновляется заранее. Callback HTTPS. Дополнительно периодический sync как восстановление после потерянного сигнала [S08].

Экспортируемое событие связывается через mapping с задачей и отдельным календарём ASCEND. Изменение ASCEND не переписывает вручную изменённое внешнее событие без выявления конфликта по версии / etag. В `v1.0` нет общей двусторонней синхронизации: внешнее изменение показывает конфликт и предлагает принять внешнее время либо повторно экспортировать локальное.

### 12.4. GitHub

GitHub App запрашивает только read-доступ к metadata, issues и pull requests выбранных репозиториев; доступ к коду, push и workflows не нужен для данного сценария. Установка приложения сама по себе не доказывает, что текущий пользователь ASCEND имеет право привязать любой installation ID: проверить пользовательскую авторизацию и доступ к репозиторию перед связыванием [S13–S15].

Webhook: читать исходные байты в допустимом размере; проверить HMAC SHA-256 по `X-Hub-Signature-256` в постоянное время; сохранить inbox с `X-GitHub-Delivery`; только после этого отвечать успешным кодом. Повторы с тем же delivery ID не запускают второй эффект [S09, S10].

Installation удалена / репозиторий исключён — закрыть доступ к его данным, убрать активные связи автоматизации и остановить задания. Issue reopened или PR без merge не считается выполнением задачи автоматически. Настройка «автовыполнение по merged PR» должна показывать, какая именно задача и какое событие участвуют.

### 12.5. Работа без внешних подключений

Полный личный цикл задачи → цель → календарь → награда → аналитика проверяется при заблокированном внешнем интернете, но доступном локальном API и PostgreSQL. Это **не** обещание полноценного offline-first режима браузера. При отсутствии связи с собственным сервером сайт показывает offline-состояние и не притворяется, что завершение сохранено.

Разрешено безопасное локальное хранение черновика формы без секретов с явным восстановлением. Кэш чувствительных ответов в service worker по умолчанию отключён. При выходе очистить кэш пользователя, черновики по выбору и состояние Query Client.

Это цели измерений, не утверждение, что ещё не написанное приложение их уже достигает. При невыполнении — зафиксировать результат, устранить причину либо официально пересмотреть требование; не ставить галочку по намерению.

### 13.2. Unit-тесты

Покрыть таблицами: переходы статусов; циклы зависимостей; расчёт целей; границы уровня; лимиты XP; отмена и восстановление entitlement; серии; окна периодов; пересечения интервалов; расчёт score; применение правила; ничья / итог испытания; цены / возвраты магазина.

Для экономики, планирования, серий и социальных разрешений целевое покрытие ветвей не ниже 85%, для backend доменных пакетов — 80% statements. Это дополнительный барьер, не замена проверкам сценариев. Генерируемый код не включается в знаменатель метрики.

### 13.3. Integration-тесты

Реальная тестовая PostgreSQL, применённые миграции и изолированные пользователи. Проверить транзакционный rollback, конкурирующие покупки / завершения, повтор jobs, доступ к чужим сущностям, возврат старой версии, каскады удаления и индексы уникальности.

Проверка 20 параллельных запросов завершения одной задачи: одна положительная награда. Проверка одновременных покупок при балансе на одну: успешна только одна. Падение worker между побочным эффектом и завершением job не создаёт второй предмет / XP.

### 13.4. End-to-end

Минимальный обязательный набор Playwright:

1. Регистрация → письмо в dev-приёмнике → подтверждение → вход.
2. Создать цель и две задачи → распределить → подтвердить день → выполнить одну.
3. Повтор завершения / отмена / повторное завершение → проверить XP и историю.
4. Привычка по расписанию → текущий период → отметка → серия и график.
5. Calendar drag & drop → проверить данные в списке; клавиатурный альтернативный перенос.
6. Focus start → pause → reload → resume → finish → confirm; другая вкладка видит активную сессию.
7. Получить достижение → купить косметику → надеть → перезайти.
8. Вступить в challenge → закончить → получить один итог; общий рейтинг без приватного текста.
9. Пригласить друга → открыть разрешённую сводку → отозвать доступ → получить отказ.
10. План перегружен → получить suggestion → предпросмотр → применить → не получить пересечения.
11. Email / push выключены → in-app уведомление работает; тихие часы соблюдены.
12. Экспорт → dry-run импорта в чистый тестовый аккаунт → импорт без XP за историю.
13. Запросить удаление → проверить выход, недоступность экспорта и очистку связей.
14. Выполнить основной личный сценарий без доступа к внешним сервисам.

Тесты провайдеров: локальные подписанные fixtures и fake API обязательны в CI; live smoke на отдельных тестовых аккаунтах перед релизом. Mock-тест не выдавать за проверенную реальную интеграцию.

### 13.5. Регрессии, которые обязательно предотвратить

- Повторный клик / retry / две вкладки не увеличивают XP.
- Дочерняя задача и родитель не получают двойной зачёт.
- Поздний перенос не улучшает прошлый подтверждённый план.
- Смена сложности выполненной задачи не выдаёт разницу XP.
- Смена часового пояса не позволяет обнулить 24-часовую квоту.
- Неделя без активности учитывается в Future Self как нулевая, а не исчезает.
- Недельная привычка не проваливается до окончания периода.
- Удалённая задача не остаётся в поисковой выдаче другого пользователя.
- Деактивированный друг / интеграция не продолжают получать данные через jobs.
- Import не принимает balance / role и не генерирует массовые «достижения впервые».
- Нет `console.log` с токеном и production seed с общим admin-паролем.
- Нельзя выполнить заранее запланированную покупку с изменённой ценой без нового подтверждения.

<a id="git"></a>
## 14. Правила Git и Definition of Done

### 14.1. Как коммитить

**Одна законченная проверяемая часть → один коммит.** Например, хранение паролей, вход, ротация refresh и экран входа — отдельные коммиты, а не один «сделал весь сайт». В каждой записи C001–C200 ниже есть точная отметка `КОММИТ СЕЙЧАС`.

Граница коммита включает реализацию, относящиеся к ней тесты, миграции и обновление контракта. Не разделять намеренно сломанную реализацию и её обязательное исправление ради количества. Если шаг слишком большой — разбить на дополнительные осмысленные коммиты `C042a`, `C042b`; 200 — плановые точки, не ограничение сверху.

Коммиты не создаются пустыми, задним числом или ради имитации активности. В этом документе 200 **плановых** коммитов; сам Markdown не означает, что такой Git-репозиторий уже существует.

### 14.2. Ветки и сообщения

Ветка этапа: `feat/06-quests`, `feat/11-progression`, `feat/22-google-calendar`. `main` должен оставаться работоспособным. Незавершённые модули доступны под feature flag и не показаны пользователю как готовые.

Формат сообщения:

```text
feat(auth): add login and session creation
fix(calendar): preserve local dates when moving all-day events
test(progression): cover concurrent reward grants
docs(api): document quest completion contract
chore(ci): run lint and integration tests
refactor(goals): isolate progress calculation
```

Номера Cxxx включать в тело коммита / issue, например `Spec: C026; F01`. Не использовать `update`, `final`, `fix all` без смысла. На merge сохранять небольшие коммиты через обычный merge или rebase merge; **не squash всего этапа**, если цель — читаемая подробная история. Не переписывать уже общую опубликованную историю без согласования команды.

### 14.3. Обязательный контроль перед каждым коммитом

```text
[ ] Одна логическая часть закончена и соответствует текущему Cxxx.
[ ] Изменения просмотрены через git diff.
[ ] Нет .env, токенов, дампов личных данных и лишних бинарников.
[ ] Код форматирован, линтер и затронутые тесты зелёные.
[ ] Есть негативный тест на изменённое правило / границу доступа.
[ ] Контракт API и миграции согласованы, если они изменены.
[ ] UI умеет loading / error / empty и не содержит фиктивных метрик.
[ ] Кнопка в интерфейсе действительно делает действие.
[ ] Нужные файлы добавлены явно, diff --cached проверен.
```

Рабочий пример после реализации:

```bash
make check-changed
# Просмотреть результат, затем:
git diff
git add services/api/internal/auth services/api/tests/integration/auth_test.go
# Указать также связанные миграции/контракт, если они менялись.
git diff --cached
git commit -m "feat(auth): add login and session creation" -m "Spec: C026; F01"
```

`make check-changed` нужно реализовать на этапе 01. Если анализ изменённых модулей недоступен, команда запускает полный набор проверок, а не пропускает их.

### 14.4. Завершение этапа

Все восемь C-пунктов этапа выполнены, соответствующий сквозной сценарий проходит, CI зелёный, README / runbook обновлён, демо-данные отделены от настоящих. Далее code review / самопроверка diff, merge, push и релизный tag там, где указан. Push рекомендуется после проверенной рабочей сессии и обязательно перед переходом к следующему этапу.

Нельзя считать этап готовым только потому, что экран похож на макет. Формальные условия F-модулей имеют приоритет над удобным количеством коммитов.

## 18. Развёртывание и эксплуатация

### 18.1. Окружения

**Development:** frontend, API, worker, PostgreSQL, локальный mail receiver и приватное файловое хранилище. Seed демо по отдельной команде. Основная работа не требует ключей Google, GitHub, облака или ИИ.

**Test / CI:** изолированная PostgreSQL, fake providers, воспроизводимый Clock и seed. Секреты для live-проверок не выдаются workflow непроверенного pull request. Live smoke выполняется в защищённом окружении с отдельными тестовыми аккаунтами.

**Staging:** HTTPS, реальные production-адаптеры, но тестовые пользователи и источники. Перед публичным релизом — миграции, live smoke и restore rehearsal.

**Production:** web/API/worker в закреплённых версиях образов; PostgreSQL и blobs с резервированием; HTTPS proxy; закрытые внутренние порты; non-root процессы; ограниченные service accounts; мониторинг и ротация секретов.

### 18.2. Переменные конфигурации

| Группа | Примеры |
|---|---|
| Режим и адреса | `APP_ENV`, `APP_ORIGIN`, `API_PORT`, `DATABASE_URL`, `LOG_LEVEL` |
| Сессии | `JWT_SIGNING_KEY`, `JWT_KEY_ID`, `JWT_ISSUER`, `JWT_AUDIENCE`, `TOKEN_ENCRYPTION_KEY` |
| Почта | `MAIL_DRIVER`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM` |
| Файлы | `BLOB_DRIVER`, `BLOB_PRIVATE_DIR`, `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `UPLOAD_SCAN_MODE` |
| Google | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` |
| GitHub | `GITHUB_APP_ID`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET` |
| Push | `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` |
| Задания | `WORKER_CONCURRENCY`, `JOB_POLL_INTERVAL`, `JOB_MAX_ATTEMPTS` |
| Флаги | `FEATURE_SOCIAL`, `FEATURE_GOOGLE_CALENDAR`, `FEATURE_GITHUB`, `FEATURE_MYSTERY_REWARDS` |

Секретные значения не помещаются в переменные frontend с публичным префиксом. VAPID public key является публичным по назначению; private key — только серверный. Нет AI-переменных. При выключенном модуле связанные маршруты явно недоступны, а навигация не предлагает неработающее действие.

### 18.3. Команды, которые должны существовать к v1.0

```bash
make dev                 # Поднять локальное окружение
make migrate             # Применить миграции к явно указанной БД
make seed                # Идемпотентный системный каталог без личных демо-данных
make seed-demo           # Только dev/test; отказ в production
make lint
make test                # Unit + component
make test-integration
make test-e2e
make check-changed       # Затронутые проверки или безопасный полный набор
make build
make backup              # Конкретное окружение выбирается явно
make restore-verify      # Только изолированное целевое окружение
```

Опасные операции не должны по умолчанию очищать текущую БД. Миграции, требующие удаления колонки, проходят схему expand → переход к новому коду → contract в отдельном релизе. Откат приложения не подразумевает автоматически безопасный rollback произвольной миграции.

### 18.4. Backup, очистка и эксплуатационные события

Backup БД ежедневно, blobs по той же политике; зашифрованная копия вне основного сервера; хранение до 30 дней. Согласованность ссылок и файлов проверять manifest. Цель RPO — 24 часа, RTO — 4 часа; реальные результаты восстановления записывать.

Подтверждённое удаление аккаунта немедленно закрывает доступ, основная очистка завершается целевым сроком до 24 часов. Остатки в изолированных backup исчезают по сроку до 30 дней. При восстановлении старой копии применить отдельно сохранённый минимальный реестр завершённых удалений **до открытия пользовательского доступа**, чтобы удалённый аккаунт не появился снова. Реестр хранит только технический ID и момент удаления, без содержимого аккаунта.

Метрики: длительность/ошибки API, активные сессии без токенов, длина очереди, возраст старейшего job, outbox lag, неудачные доставки, sync age, ошибки ledger reconciliation, использование диска / blobs. Алерт не должен включать текст личной задачи.

Необходимые runbooks: отказ БД, переполнение диска, остановка worker, ошибочная миграция, недоступный SMTP, истёкший OAuth, потеря webhook, компрометация секрета, отказ quarantine scanner, конфликт восстановления из backup.

## 19. Риски и исключения

| Риск | Решение в этом ТЗ |
|---|---|
| Слишком большой объём | 25 последовательных этапов, ранние пригодные релизы; полный scope не маскируется под маленький MVP |
| Фарм опыта | Уникальные источники, контейнеры без XP, скользящие квоты, один entitlement; честно признать ограничения самоотчёта |
| Потеря мотивации из-за пропуска | Отдых, recovery, отсутствие штрафного XP, честные серии и нейтральный язык |
| Часовые пояса и повторения | Раздельные date/instant, IANA, замороженные периоды и тесты границ |
| Несогласованные графики | События, пересоздаваемые проекции, source drill-down и зафиксированные формулы |
| Двойные покупки или начисления | Транзакции, блокировки, уникальность, permanent operation IDs и конкурентные тесты |
| Утечка частных данных | Закрытые настройки, owner checks, гранулярное согласие, приватные blobs и отзыв доступа |
| Проблемы внешних API | Очередь, retry, cursors, dedupe, состояние подключения и независимое ядро |
| Платная библиотека неожиданно стала обязательной | Standard-возможности календаря, лицензии ресурсов и зафиксированные зависимости |
| Слишком много анимаций и уведомлений | Отключение эффектов, reduced motion, тихие часы и лимиты |
| Огромные технические коммиты | 200 конкретных границ, возможность дополнительного дробления и запрет фиктивного дробления |

### 19.1. Не входит в целевой v1.0

Нейросети и AI API; аппаратные устройства; платёжная система, реальные ставки и азартные награды; гарантированная верификация реального поведения; медицинские советы; распознавание речи; открытый мессенджер; публичные личные дневники; чтение всего исходного кода GitHub; автоматическая отправка заявок на работу; универсальная двусторонняя синхронизация всех календарей; полноценный браузерный offline-first; Kubernetes и микросервисы без измеренной необходимости.

«Другие интеграции» означают возможность расширения через адаптеры, а не безграничный объём неизвестных сервисов. В данном ТЗ обязательный конечный набор — Google Calendar, GitHub, ICS, email и browser push. Любой новый провайдер оформляется отдельным изменением требований.

### 19.2. Затраты

Работа без ИИ означает отсутствие оплаты AI-запросов. Это не обещание бесплатного публичного хостинга: сервер, домен, почта, файловое хранилище и обслуживание могут требовать расходов. Локальный режим должен запускаться без покупки подписки нейросети и без платного календарного UI-компонента. Конкретные тарифы здесь не фиксируются.

### 19.3. Как менять ТЗ

У изменения есть ID, причина, затронутые F/C-пункты, новая проверка и влияние на данные / миграции. Большое техническое решение записывается в ADR. Нельзя молча убирать обязательную функцию из продукта, сохраняя отметку «всё готово». Снижение scope публикуется как новая редакция ТЗ с явным списком отличий.

## 20. Первые действия разработчика

Открыть **этап 01, C001**. Создать репозиторий и положить этот файл в `docs/ASCEND_TECHNICAL_SPEC.md`. Затем реализовывать по одному C-пункту, проверять указанное поведение, отмечать галочку и делать соответствующий коммит.

Первый рабочий ориентир — `v0.1-foundation`: настоящий вход и профиль. Следующий — `v0.2-core`: задачи, цели, календарь и привычки, которыми уже можно пользоваться самому. После этого подключать XP и остальные игровые функции к существующим действиям, а не строить отдельно «красивую игру» без данных.

Для отдельного рабочего задания использовать такую форму:

```text
Требование: F04. Задачи
Пункт плана: C044. Статусы и журнал

Нужно реализовать:
- переходы start/complete/reopen/postpone/skip/fail;
- проверки владельца, версии и допустимого состояния;
- историю с исходной/новой датой и причиной;
- связанные тесты и изменение OpenAPI;
- UI-состояния загрузки, конфликта и ошибки.

Готовность: тесты проходят, перенос не сдвигает дедлайн молча,
история видна после reload, другой пользователь не имеет доступа.

После проверки:
feat(quests): implement lifecycle transitions and change history

Не включать в этот коммит: XP, магазин, переписывание дизайна всего сайта.
```

**Главный критерий готового ASCEND:** утром можно составить реалистичный план, днём выполнить реальные действия, вечером увидеть честные итоги и продолжить развитие — без зависимости от ИИ и без потери контроля над собственными данными.

## 21. Технические источники

При выборе точных версий зависимости и правила провайдеров сверяются повторно. Источники не являются утверждением, что будущая реализация уже протестирована.
