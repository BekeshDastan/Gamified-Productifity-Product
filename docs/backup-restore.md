# Резервное копирование и проверка восстановления

Backup tool использует PostgreSQL custom dump и restic (аутентифицированное
шифрование). Пароль репозитория хранить отдельно от сервера и самих копий:
без него восстановление невозможно. Локальный volume `/repository` используется
только для репетиции, он не защищает от потери хоста.

## Локальная репетиция

```sh
node scripts/release-backup.mjs init .data/release-local/release.env ascend-release-local
node scripts/release-backup.mjs backup .data/release-local/release.env ascend-release-local
node scripts/release-backup.mjs restore-drill .data/release-local/release.env ascend-release-local
node scripts/release-backup.mjs retention-preview .data/release-local/release.env ascend-release-local
```

Init выполняется один раз. Backup останавливает только edge/API/worker выбранного
release-проекта, проверяет их остановку, затем делает dump, копирует blobs и
manifest с SHA-256, размерами и количеством строк каждой таблицы. В finally
возобновляются только ранее запущенные сервисы. Требуется отсутствие других
писателей в этой базе; при нескольких репликах остановить все реплики.
Нельзя запускать два backup/обновления одновременно. На время снимка доступ
прерывается; для больших баз нужен другой подход к согласованным снимкам.

Restore разрешён исключительно в restore-db/ascend_restore и только в пустую БД.
Проверяется весь restic repository, manifest, все количества строк и соответствие
каждого неудалённого вложения контрольной сумме в восстановленной БД.
База и blobs восстановления имеют отдельные volumes. Повтор в непустую базу
отклоняется: результаты сохраняются для исследования, автоматической очистки нет.
Снимок находится в tmpfs и исчезает после завершения контейнера; для данных больше
2 ГБ изменить размер tmpfs либо использовать отдельный зашифрованный staging-диск.

## Независимое хранилище и расписание

В BACKUP_ENV_FILE задать RESTIC_REPOSITORY на S3/SFTP/REST у другого провайдера
или физически другом сервере, RESTIC_PASSWORD и необходимые credentials. Пример
S3: `s3:https://storage.example.net/ascend-backups`; секреты сюда не добавлять.
Не использовать ту же учётную запись для удаления production и off-site backups.
Проверить восстановление с независимой машины и хранение пароля вне хоста.

Шаблоны systemd service/timer в deploy: ежедневный запуск около 03:00, пропущенный
запуск догоняется после загрузки. Перед установкой проверить пути Node/репозитория
и пользователя ascend с доступом Docker; Docker socket даёт административный
доступ к хосту, этому пользователю нельзя давать посторонние задачи.
Плановый RPO при ежедневном успешном backup — до 24 часов плюс задержка timer.
Контролировать успешный запуск, не только наличие таймера.

Политика хранения: 30 ежедневных и 12 недельных снимков. `retention-preview`
показывает кандидатов; после успешного restore и проверки независимой копии
оператор применяет `restic forget --host ascend --tag ascend-consistent
--keep-daily 30 --keep-weekly 12 --prune` внутри backup-контейнера с теми же
настройками. Удаление старых копий намеренно не совмещено с первым backup.

## Фактические результаты

Результаты локального restore drill и длительности публикуются в
`docs/release-acceptance.md`. Snapshot age — возраст выбранной копии при проверке;
это не доказательство RPO будущего сервера. Перед публичным запуском проверить
объём реальных данных, off-site доступ и время полного восстановления приложения.
