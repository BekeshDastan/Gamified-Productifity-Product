# Мониторинг и аварии

Подключить compose.monitoring.yaml к основному compose с тем же env/project.
OPS_BEARER_TOKEN в приватном env и файл METRICS_TOKEN_FILE содержат одинаковые
случайные 32 байта в base64. API слушает приватный 9090; edge закрывает /metrics.
Prometheus UI доступен только на loopback хоста:19090 (для сервера — SSH tunnel).
Не публиковать его в интернет. Данные хранятся 15 дней в отдельном volume.

Измеряются HTTP histogram по зарегистрированному шаблону маршрута, методу и
классу статуса, количество/возраст jobs и outbox, dead letters, истёкшие leases,
worker heartbeat и свободное место на разделе blobs (Linux). Тела, query string,
имена пользователей и ID владельцев в labels не включаются. Heartbeat ставится
основным циклом worker; зависший обработчик не поддерживает ложную активность.

Пороги: API/БД недоступны 1 мин, heartbeat старше 60 секунд ещё 1 мин,
queue/outbox lag >120 секунд 2 мин, dead jobs 1 мин, зависшие leases 2 мин,
свободно <10% диска 5 мин, доля HTTP 5xx >5% в течение 2 мин.
Это начальные пороги; настройка под реальную нагрузку обязательна.
Правила создают alerts в Prometheus. Внешний Alertmanager/канал оператора
пока не настроен: наличие firing alert не означает доставку человеку.

Локальная проверка: `node scripts/release-ops-smoke.mjs` останавливает только
worker проекта ascend-release-local, ждёт firing alert, запускает его обратно
и ждёт разрешения. Результат — `.data/release-local/operations-result.json`.
Отдельный PostgreSQL-тест проверяет dead jobs/отсутствующий heartbeat и очистку
состояния; существующий jobs test — потерю lease, повтор, retry и единственный эффект.

## API или БД недоступны

Проверить /health/live и /health/ready, состояние контейнеров, место и соединения
БД. Не перезапускать миграции вслепую и не выполнять down --volumes.
При недоступной БД API readiness и scrape возвращают 503. Восстановить сеть/БД,
проверить readiness и запись в отдельной тестовой задаче. Если данные повреждены,
использовать изолированный restore drill, затем согласованное переключение.

## Worker или почтовый провайдер

Проверить heartbeat, lag, SMTP STARTTLS/credentials и redacted error codes.
После восстановления включить worker; lease истекает и будет захвачен заново.
Не обнулять dedupe_key и не удалять ledger/idempotency для «повторной попытки».
Не отправлять письма ручным обходом очереди. Истёкшая/отменённая доменная операция
должна оставаться отменённой. Если провайдер подтвердил приём неоднозначно,
повтор письма возможен, но ссылка одноразовая; награда не начисляется повторно.

## Dead-letter triage

Оператор с доступом БД смотрит только id/kind/attempts/last_error_code,
не копирует payload в логи или чат. Сначала исправить причину и определить,
поддерживает ли обработчик безопасный повтор с прежними источником и dedupe_key.
Сохранить основание решения в операторском журнале. Повтор нельзя делать
массовым UPDATE всех dead jobs. Создать исправление конкретного обработчика
и тест его replay либо отменить подтверждённо устаревшую операцию.

## Диск или антивирус

При нехватке места остановить новые загрузки, проверить backup repository,
логи и retention. Не удалять blobs по возрасту без сверки references в БД.
При недоступном scanner файлы остаются pending и недоступны для скачивания.
Восстановить clamd/подписанные сигнатуры; повторить проверку через штатное действие.
Никогда не менять verdict на clean SQL-запросом.

## Перед внешним запуском

Настроить канал оповещений, проверить доставку с контролируемым сбоем и подтвердить
дежурного. Проверить alert на потерю backup расписания/независимого хранилища
в системе сервера. Пока этих ресурсов нет, это остаётся внешней приёмкой.
