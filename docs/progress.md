## Этап 04

- C025: users с нормализованным уникальным email и серверной role по умолчанию;
  регистрация и audit атомарны. Argon2id: 64 MiB, t=3, p=2, случайная соль 16 байт,
  ключ 32 байта; максимум две параллельные операции хеширования на процесс.
  Пароль 12–128 Unicode-символов / до 512 байт, без обрезания пробелов.
  Публичный HTTP endpoint пока не подключён: сначала C026–C027 (сессии, CSRF,
  ограничения попыток). Это серверный шаг; экран регистрации ещё недоступен.
  Проверено: 8 параллельных регистраций дают 1 user и 1 audit; невалидный ввод
  не пишет строки; отказ audit откатывает создание. Хеш исключён из JSON моделей
  sqlc; повреждённые параметры PHC отвергаются до выделения памяти. Go unit,
  integration, vet/Staticcheck, web typecheck и Go build прошли.

- C026: вход проверяет Argon2id, неизвестный email проходит равную по стоимости
  проверку. Серверная сессия 7/30 дней, JWT HS256 на 15 минут с обязательными
  sub/sid/iss/aud/iat/exp/jti; роль и действительность сессии проверяются в БД.
  Refresh — случайные 256 бит, хранится SHA-256. Production cookie __Host-,
  Secure/HttpOnly/SameSite=Lax, локальный HTTP разрешается явно только на loopback.
  Без «Запомнить меня» cookie живут до закрытия браузера, абсолютный срок сессии 7 дней.
  Пароль повторно проверяется под блокировкой пользователя после Argon2id, создание
  сессии, refresh и audit атомарно. HTTP подключается следующим шагом C027.
  Проверены неверные claims/алгоритм/ключ, истечение, отзыв, актуальная роль,
  изоляция двух аккаунтов, SHA-256 в БД и откат при отказе audit. Unit/integration прошли.
  CI C025 завершился успешно: run 38212471251.

- C027: HTTP register/login/session/csrf подключены. Origin совпадает с APP_ORIGIN,
  mutation принимает JSON + связанный с cookie CSRF; защищённый запрос дополнительно
  связывает CSRF именно с sid access cookie. Pre-auth cookie подписан и живёт 30 минут.
  Лимиты в PostgreSQL атомарны между процессами: 5 неудач account+IP / 15 минут,
  50 / IP, регистрация 10 / IP, пользовательский API 120 / минуту. Пороги настраиваются;
  клиент получает Retry-After. Успех освобождает allowance неудачных попыток.
  IP берётся из соединения; непроверенные Forwarded/X-Forwarded-For игнорируются.
  Для production reverse proxy отдельная настройка доверия пока не реализована:
  лимит IP видит адрес proxy, что требует учёта при развёртывании.
  Реальная HTTP/PostgreSQL-проверка: чужой Origin/CSRF не создаёт user,
  10 параллельных неверных входов дают ровно 5 × 401 и 5 × 429; окно восстанавливается.
  Новый случайный ключ сохранён только в ignored .env; инструкция генерации в README.

- C028: refresh rotation атомарна и сохраняет абсолютный срок сессии. Повтор
  в течение 5 секунд — 409 REFRESH_IN_PROGRESS без Set-Cookie и без новых токенов;
  поздний повтор отзывает всю семью в БД до возврата 401. Другие устройства не затронуты.
  Logout работает и после истечения access; logout-all, список активных устройств
  и отзыв отдельной сессии доступны только владельцу. Токены после отзыва не действуют.
  Реальные HTTP/PostgreSQL-тесты: 8 конкурентов дают 1 successor и 7 конфликтов,
  проверены точная граница 5 секунд, family revocation, потерянный Set-Cookie,
  logout, logout-all и 404 на чужую сессию. Сбой восстановления требует нового входа;
  сервер не возвращает прежние credentials и не продлевает абсолютные 7/30 дней.

- C029: HTTP-регистрация атомарно создаёт 24-часовой одноразовый email token и outbox.
  Worker доставляет ссылку через SMTP; повторная доставка после неопределённого
  результата SMTP возможна, ссылка остаётся той же и одноразовой. В БД только SHA-256;
  outbox/jobs содержат ID. Opaque token восстанавливается worker через отдельный
  HMAC-контекст и случайный UUID, открытый token/link в БД не хранится. Смена ключа
  инвалидирует ещё не использованные ссылки. URL fragment исключает token из
  HTTP URL/Referer; подтверждение только POST. Resend 3/час user и IP, предыдущие
  ссылки отзываются. Общая RequireVerified-защита проверена для будущих публикаций.
  Проверены 8 одновременных подтверждений (1 успех), истечение ровно через 24 часа,
  resend/лимит, отсутствие raw token в очереди и откат регистрации при отказе outbox.

- C030: forgot-password всегда ставит одинаковую задачу и возвращает один DTO;
  lookup аккаунта выполняет worker. Email в задаче зашифрован AES-GCM с отдельным
  контекстом ключа. Неизвестным/отключённым аккаунтам письма не отправляются.
  Reset token 30 минут, SHA-256 в БД, одноразовый POST; после нового Argon2id
  все старые сессии и reset links отзываются одной транзакцией с audit.
  Общие лимиты mail/token настраиваются через AUTH_MAIL_REQUESTS/AUTH_TOKEN_ATTEMPTS.
  Проверены одинаковые ответы/queue path, отсутствие plaintext email в запросе
  очереди, неизвестный адрес без письма, истечение, повтор, запрет смешения verify/reset,
  старый/новый пароль, access+refresh двух устройств и rollback при ошибке audit.

- C031: формы login/register/verify/forgot/reset подключены к Go API; подтверждение
  одноразовых ссылок только по кнопке, fragment сразу очищается из адреса.
  Password managers/Unicode/пробелы поддержаны; валидация, busy lock, safe errors,
  remember-me 30 дней и ограниченный внутренний redirect. Токены только HttpOnly,
  CSRF/состояние аккаунта в памяти. BroadcastChannel передаёт лишь changed/signed-out,
  Web Locks сериализует cookie mutations; потеря refresh не маскируется успешным входом.
  Панель показывает актуальную почту, resend, устройства и отзыв/выход.
  Кэш аккаунта изолирован в AppShell и очищается при смене; auth forms находятся
  вне этой границы, поэтому не теряют fragment при начальной проверке сессии.
  Проверено в Chromium production: регистрация → реальный worker/SMTP/Mailpit →
  verify → два независимых устройства → forgot/reset → старые входы отозваны →
  старый пароль отклонён → новый пароль работает. Внешний redirect запрещён;
  30 web unit и существующие 13 UI E2E проходят. Набор запускается явно через
  npm run test:auth-e2e, использует отдельную случайную схему ascend_test.

- C032: браузерная приёмка дополнена двумя вкладками с одним refresh, немедленным
  logout через BroadcastChannel и потерянным реальным refresh-ответом без Set-Cookie.
  Повторный вход восстанавливает доступ; credentials не появляются в console/storage.
  Проверены формы 360 px в обеих темах, WCAG и скриншоты; мобильные экраны осмотрены.
  Добавлены unit-проверки Origin/Content-Type/pre-auth cookie/30-минутного срока,
  безопасной конфигурации и недоверенных Forwarded headers. Общий Protect теперь
  применяет user quota и к будущим private routes, refresh учитывает тот же лимит;
  обычный logout остаётся доступен при исчерпании квоты. Восстановление квоты проверено.
  Четыре настоящих browser auth сценария включены в check-changed и integration CI.
  Смена пароля с текущим паролем остаётся запланированным C037; этап 04 принимает
